## Root cause found by live diagnosis (why the first restart logged nothing)
After the owner's first restart + approval, a live `studio_status` still produced no log line and no `hook_errors.log`. I diagnosed with a force-loaded (`--extension`) throwaway probe hook (`logs/tasks/p1t03_diag.ts`, deleted) + a fresh-session `get_state` (`dumpTools`): **there is NO native `mcp__unsloth_studio__<tool>` tool.** MCP is reached through the **`write` tool targeting a `xd://mcp__unsloth_studio_<tool>` device path** (this harness), an **`mcp` dispatcher tool** (server+tool in args), or a legacy namespaced name. So the hook's original `startsWith("mcp__unsloth")` filter rejected **every** real call → empty log, even though the hook loaded fine. (Note: a fresh `--mode rpc` session had no MCP mounted at all — MCP is host-mounted only in the interactive agent harness — so `dumpTools` there lists just the 11 built-ins; the `mcp` tool + `xd://mcp__` devices are what the real session exposes.)

**Fix (committed):** the hook now derives the Studio tool from all three surfaces (`write`/`read`/`edit` to a `xd://mcp__unsloth…` path, the `mcp` dispatcher with an unsloth server, or a native `mcp__unsloth…` name) and ignores plain writes / other servers / bash. Path regex accepts a single or double underscore delimiter (`studio_<tool>` is the real form). Regression test `logs/tasks/p1t03_hooktest.ts` fires all surfaces with realistic shapes → **10/10 green** (device `write`→studio_status ok, `get_job` fail→ok:false, native `list_models`, `mcp` dispatcher, plus ignored file-write/other/bash; redaction, UTF-8 `café × “q”`, and `duration_s` all intact).
